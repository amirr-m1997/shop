  ## ایرادهای بحرانی

  1. تصاحب سفارش‌های مهمان با ثبت‌نام یک ایمیل

  در ثبت‌نام معمولی، ایمیل قبل از تأیید به کاربر متصل می‌شود و سپس تمام سفارش‌های
  مهمان دارای آن ایمیل به حساب جدید انتقال می‌یابد:

  - backend/accounts/views.py:101
  - backend/accounts/views.py:178

  بنابراین مهاجم می‌تواند با ایمیل قربانی ثبت‌نام کند و سفارش‌ها، پرداخت‌ها و
  آدرس‌های مهمان او را تصاحب کند. انتقال سفارش باید فقط پس از تأیید ایمیل یا با
  ارائه شناسهٔ نشست/توکن اختصاصی سفارش انجام شود.

  2. یکتا نبودن ایمیل در سطح دیتابیس

  قبل از ثبت‌نام فقط exists() اجرا می‌شود، اما فیلد ایمیل مدل پیش‌فرض Django یکتا
  نیست. دو درخواست هم‌زمان می‌توانند دو حساب با یک ایمیل بسازند. این وضعیت ممکن
  است بازیابی رمز را نیز به MultipleObjectsReturned و خطای ۵۰۰ برساند.

  راه‌حل صحیح، constraint یکتا روی ایمیل نرمال‌شده در دیتابیس و مدیریت
  IntegrityError است.

  3. تنظیمات فعلی برای انتشار امن نیست

  check --deploy شش هشدار داد:

  - DEBUG=True
  - کلید امنیتی ضعیف
  - HTTPS redirect غیرفعال
  - HSTS غیرفعال
  - کوکی Session بدون Secure
  - کوکی CSRF بدون Secure

  منطق تنظیمات قابلیت امن‌شدن را دارد، ولی فایل محیط فعلی برای production مناسب
  نیست. تنظیمات مربوطه در backend/shop/settings.py:27 و backend/shop/
  settings.py:405 قرار دارد.

  ## باگ‌ها و مشکلات مهم

  4. تنظیم پیش‌فرض CORS اشتباه تایپی دارد

  مقدار پیش‌فرض با CORS_ALLOWED_ORIGINS= شروع شده و بنابراین اولین origin نامعتبر
  است:

  backend/shop/settings.py:35

  همچنین پورت پیش‌فرض FRONTEND_URL برابر ۵۱۷۳ است، درحالی‌که Vite روی پورت ۳۰۰۰
  اجرا می‌شود.

  5. لاگ درخواست‌ها همیشه کاربر را anonymous ثبت می‌کند

  middleware ثبت لاگ قبل از middleware احراز هویت قرار گرفته است؛ بنابراین هنگام
  ثبت context هنوز request.user مشخص نشده است. خروجی تست‌ها نیز این ایراد را
  تأیید کرد: حتی درخواست‌های احرازشده با user=anonymous لاگ شدند.

  - backend/shop/settings.py:87
  - backend/shop/middleware.py:38

  این موضوع ممیزی امنیتی و ردیابی رخدادهای کاربران را غیرقابل‌اعتماد می‌کند.

  6. جعل IP در بعضی لاگ‌های امنیتی

  log_security_event همیشه X-Forwarded-For را قبول می‌کند، حتی وقتی
  TRUST_PROXY_HEADERS=False باشد:

  backend/accounts/security.py:234

  مهاجم می‌تواند IP ثبت‌شده در لاگ‌های امنیتی را جعل کند. تابع _get_client_ip این
  کار را درست انجام داده، ولی همه‌جا از آن استفاده نشده است.

  7. تأخیر ورود، worker سرور را مسدود می‌کند

  مکانیزم progressive delay از time.sleep() داخل request استفاده می‌کند:

  backend/accounts/security.py:93

  در حملهٔ انبوه، هر درخواست می‌تواند worker را ۲ تا ۵ ثانیه اشغال کند و خودش به
  ابزار DoS تبدیل شود. در تست‌ها یک درخواست ورود ناموفق حدود ۲٫۶ ثانیه طول کشید.

  8. شمارنده‌های امنیتی بدون Redis قابل اتکا نیستند

  در نبود REDIS_URL، از LocMemCache استفاده می‌شود:

  backend/shop/settings.py:386

  در deployment چندپردازشی، هر worker شمارندهٔ rate-limit و lockout جداگانه دارد؛
  مهاجم با جابه‌جایی بین workerها می‌تواند محدودیت را دور بزند.

  9. ارسال پیامک هنوز پیاده‌سازی نشده

  در مسیر OTP تلفن یک TODO صریح وجود دارد:

  backend/accounts/views.py:499

  موفق می‌دهد.

  10. خطاهای ارسال ایمیل در چند مسیر بلعیده می‌شوند

  چندین except Exception عمومی وجود دارد و بعضی مسیرها حتی pass می‌کنند. در نتیجه
  ممکن است عملیات موفق گزارش شود ولی ایمیل وضعیت سفارش یا پرداخت ارسال نشده
  باشد؛ بدون retry یا ثبت وضعیت شکست.

  نمونه: backend/dashboard/views.py:127

  11. مستندات پروژه قدیمی و ناسازگار است

  README پروژه را Django 4.2 معرفی می‌کند، ولی requirements از Django 5.2 استفاده

  ## عوامل کاهش سرعت سایت

  12. صفحه‌بندی محصولات بیش از حد بزرگ است

  API محصولات در هر صفحه ۱۰۰ محصول برمی‌گرداند و برای همهٔ آن‌ها تصاویر، سایزها و
  رنگ‌های variant را prefetch می‌کند:

  backend/products/views.py:118

  این یعنی payload سنگین، مصرف حافظه بالا و زمان serialization زیاد، خصوصاً وقتی
  هر محصول چند تصویر و variant داشته باشد. اندازه مناسب معمولاً ۲۰ تا ۳۰ محصول
  است.

  13. endpoint صفحهٔ اصلی می‌تواند دادهٔ بسیار بزرگی تولید کند

  برای هر بخش صفحهٔ اصلی، query جداگانهٔ محصولات، تصاویر، برند و دسته‌بندی اجرا
  می‌شود:

  backend/products/views.py:217

  اگر محصولات در چند section تکرار شوند، هم query و هم serialization تکراری
  خواهد بود. پاسخ صفحهٔ اصلی نیز caching سمت سرور ندارد.

  14. تولید تصویر به‌صورت synchronous داخل request انجام می‌شود

  اولین درخواست هر اندازه/فرمت، فایل اصلی را باز می‌کند، resize و WebP/AVIF
  encode انجام می‌دهد:

  backend/shop/image_views.py:46

  AVIF و WebP عملیات CPU-intensive هستند. با چند درخواست هم‌زمان برای تصویر جدید،
  workerهای Django اشغال می‌شوند. همچنین lock مشخصی برای جلوگیری از تولید هم‌زمان
  یک variant وجود ندارد. بهتر است تصاویر هنگام upload یا در worker پس‌زمینه ساخته
  و سپس توسط Nginx/CDN سرو شوند.

  15. تعداد بیش از حد variant تصویر

  کامپوننت تصویر برای هر عکس تا هفت عرض WebP و هفت عرض AVIF معرفی می‌کند:

  frontend/src/components/ui/ResponsiveImage.jsx:1

  مرورگر فقط یکی را دانلود می‌کند، اما سرور و cache به‌مرور variantهای بسیار زیادی
  تولید می‌کنند. بعضی تصاویر پروژه هم هنوز مستقیماً از <img> استفاده می‌کنند و اصلاً
  وارد مسیر بهینه‌سازی نمی‌شوند.

  16. لاگ‌نویسی synchronous برای تمام پاسخ‌های موفق

  هر درخواست موفق در فایل چرخشی نوشته می‌شود و بعضی رویدادها در چند فایل تکرار
  می‌شوند:

  backend/shop/settings.py:430

  روی ترافیک بالا، I/O دیسک و lock مربوط به فایل‌های log می‌تواند latency ایجاد
  کند. لاگ access بهتر است بر عهده reverse proxy باشد و لاگ اپلیکیشن به stdout
  یا سامانهٔ متمرکز ارسال شود.

  17. SQLite در حالت پیش‌فرض

  اگر DB_NAME تنظیم نشود پروژه سراغ SQLite می‌رود:

  backend/shop/settings.py:282

  SQLite برای فروشگاه پرترافیک، ثبت سفارش هم‌زمان و رزرو موجودی مناسب نیست و
  هنگام writeهای هم‌زمان lock ایجاد می‌کند. production باید حتماً PostgreSQL باشد.

  18. جست‌وجوی متنی پرهزینه

  جست‌وجوی محصول و بلاگ با icontains روی چند فیلد، از جمله description/content

  - backend/blog/views.py:30
  - backend/products/views.py:127

  برای PostgreSQL بهتر است Full Text Search و indexهای GIN/Trigram اضافه شود.

  19. N+1 در بعضی serializerهای داشبورد

  برای هر کاربر obj.orders.count() اجرا می‌شود:

  backend/dashboard/serializers.py:24

  هرچند queryset سفارش‌ها را prefetch کرده، فراخوانی count() ممکن است بسته به
  cache/queryset به queryهای اضافی منجر شود. بهتر است Count('orders') در
  queryset annotate شود. همین الگو برای تصاویر و variantهای محصول نیز در بعضی
  serializerها دیده می‌شود.
